# 드리프트 경고가 원인을 단정한다

검색·인용이 붙은 대화에서 이 경고가 뜬다.

```
[warn] 스트림 본문이 원본과 21% 어긋난다 (스트림 636자 / 원본 810자).
       화면은 원본 기준으로 교정했습니다. 델타 파서가 일부 op 를 놓치고 있다는 뜻입니다.
```

**마지막 문장이 문제다.** 실측해보니 델타 파서가 멀쩡한데도 이 경고가 뜬다.

## 실측 (2026-09-08)

같은 대화(`6a9f9e1b…`, 인용 3건 + 출처 각주)에서 검색이 붙는 질문을 보내고
스트림의 모든 델타를 경로·연산·길이로 추적했다. 빌드 `2026-09-08 10:30`.

**우리 확장이 낸 경고**

```
스트림 2271자 / 원본 312자 → 628% 어긋남
```

**실제 값**

| 무엇 | 길이 |
|---|--:|
| 백엔드에 저장된 최종 응답 (`end_turn: true`) | **2488자** |
| 우리가 스트림에서 누적한 것 | 2271자 (실제의 **91%**) |
| `verify` 가 fiber 에서 읽어온 것 | **312자** (실제의 12%) |

**[확정] 짧았던 쪽은 스트림이 아니라 fiber 다.** 스트림은 실제의 91% 를 담았고,
비교 대상으로 삼은 fiber 가 12% 짜리 조각이었다. 경고는 그 조각을 '원본' 이라 부르며
델타 파서를 지목했다.

fiber 가 조각을 돌려주는 것은 처음 본 것이 아니다. 인용 마커를 조사할 때도
**본문 641자인데 fiber 가 196자**인 순간을 기록해 뒀다
([2026-09-04](2026-09-04-citation-markers-shown-raw.md) 문서의 "2차 실측" 절).
스트리밍이 끝난 직후 원본이 다시 그리는 동안 그렇게 된다.

## 왜 기존 가드가 못 막나

이미 이런 경우를 위한 재검증이 있다 (`src/content/index.js`).

```js
// 원본이 아직 그리는 중이면 fiber 가 스트림보다 짧고, 스트림의 접두사다.
if (streamed && fiber.length < streamed.length && streamed.startsWith(fiber)) {
  … 900ms 뒤 한 번 더 verify …
}
```

**`startsWith` 가 조건이다.** 두 가지 이유로 자주 어긋난다.

**1. 인용 마커의 표기가 다르다.**
같은 인용을 스트림은 PUA 봉투로, fiber 는 `:contentReference` 로 준다
(2026-09-04 문서에서 확정).

```
스트림 : citeturn692576search1      약 29자
fiber  : :contentReference[oaicite:0]{index=0}        36자
```

**첫 인용이 나오는 지점부터 두 문자열이 갈라진다.** 그 뒤로는 fiber 가 아무리
정당한 접두사라도 `startsWith` 가 거짓이 된다. 인용이 있는 대화에서는 이 가드가
사실상 꺼져 있는 셈이다.

**2. 조각이 접두사가 아닐 수 있다.**
312자짜리 fiber 는 본문 앞부분이 아니라 다른 조각이었다. 접두사 검사로는 못 걸러낸다.

## 사용자가 본 경우(21%)는 방향이 반대다

```
스트림 636자 / 원본 810자      ← 스트림이 짧다
```

이 방향은 **표기 차이만으로는 설명되지 않는다.** 인용 하나당 fiber 가 약 7자 길지만
(29 → 36), 174자를 채우려면 인용이 25개 있어야 한다. 그러니 이 경우에는
**스트림이 실제로 무언가를 놓쳤을 가능성이 있다.** 다만 이번 실측에서는 재현되지 않았다.

이번에 추적한 델타의 경로 분포는 이랬다.

```
/message/content/parts/0                     31건
(경로 생략 — 직전 경로를 잇는다)              18건   전부 parts/0 을 상속
/message/metadata/content_references           7건
/message/metadata/safe_urls                    3건
/message/content/thoughts                      2건
/message/metadata/content_references/0/alt     2건
…
```

**[가정] 경로 생략 델타가 메타데이터 경로를 상속하면 본문이 버려진다.**
본문 델타는 `content/parts/\d+$` 에 걸릴 때만 받는데, 경로를 생략한 델타는
`lastPath` 를 잇는다. 바로 앞이 `/message/metadata/…` 였다면 그 본문은 버려진다.
이번 18건은 전부 `parts/0` 을 상속해 무사했지만, 순서가 달라지면 샌다.
→ 메타데이터 경로가 `lastPath` 를 덮지 않게 하면 이 위험은 사라진다.

## 수정 방안

**1. 경고 문구에서 원인 단정을 뺀다.** 지금은 관측(길이 차이)과 해석(파서가 놓쳤다)을
한 문장에 섞어 놓았다. 실측에서 그 해석이 틀린 경우가 나왔다. 관측만 적는다.
(문구가 반말이기도 하다 — "어긋난다".)

**2. 비교 전에 표기를 맞춘다.** 양쪽에서 인용 마커를 지우고 비교한다. 이미
`markdown.js` 가 두 표기를 다 아는 정규식을 갖고 있다. 그러면 인용 유무와 무관하게
같은 기준으로 잰다.

**3. fiber 가 '아직 안 그려진 것' 인지 판단한다.** 접두사 검사 대신 **길이 비율**로 본다.
fiber 가 스트림의 절반도 안 되면 그건 원본이 아직 그리는 중이라고 보고 재검증한다.
지금은 한 번만 다시 보는데, 두세 번으로 늘린다.

**4. 정본을 API 로 바꾼다.** `conversation.load()` 가 이미 백엔드에서 최종 본문을
받아온다(위 표의 2488자). fiber 조각보다 그쪽이 확실하다. 스트림이 끝난 뒤
그 대화를 다시 읽어 비교하면 이 경고의 신뢰도가 근본적으로 올라간다.

**5. 메타데이터 경로가 `lastPath` 를 덮지 않게 한다.** `/message/content/…` 만
`lastPath` 로 기억한다. 위 [가정] 을 없애는 값싼 방법이다.

## 고친 방법 (2026-09-08)

방안 다섯 개 중 넷을 넣었다.

- `markdown.stripMarks()` — 두 표기(PUA·`:contentReference`)를 걷어낸다.
  `markdown.js` 가 이미 두 정규식을 갖고 있어 그걸 그대로 내보냈다
- `health.reconcile()` — **걷어낸 뒤 비교한다.** 인용 유무와 무관하게 같은 기준으로 잰다.
  경고 문구에서 원인 단정을 뺐다 — 관측(길이 차이)만 적고 `:health` 를 가리킨다
- `verify` 수신부 — 접두사 검사를 버리고 **길이 비율**로 본다.
  fiber 가 스트림의 절반도 안 되면 아직 안 그려진 것으로 보고 **세 번까지** 재검증한다
  (간격도 900ms → 1.8s → 2.7s 로 늘린다). 끝내 조각이면 **그걸 정답이라 부르지 않고
  스트림 본문을 유지한다.** 전에는 조각으로 화면을 덮고 경고까지 냈다
- `tap.js` — 이어받을 경로(`lastPath`)를 **본문 경로일 때만** 갱신한다.
  `/message/content/…` 만 기억하므로 메타데이터 델타가 끼어도 뒤따르는
  경로 생략 델타가 본문으로 들어간다

넣지 않은 것: **정본을 API 로 바꾸는 것(4번).** fiber 판정이 이제 훨씬 보수적이라
급하지 않고, 스트림 종료 직후 대화를 다시 읽는 것은 별도 왕복이 든다. 남겨 둔다.
