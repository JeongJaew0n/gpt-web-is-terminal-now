# 다국어 도입 검토

웹스토어에 올릴 준비를 하면서 나온 질문이다. 지금은 화면 문구가 전부 한국어다.

결론부터 — **할 수 있고, 규모는 크지만 어렵지는 않다.** 다만 크롬의 기본 방식
(`chrome.i18n`)만으로는 이 앱에 필요한 것을 다 못 채운다. 두 가지를 섞어야 한다.

## 1. 얼마나 되나 (실측 2026-09-08)

`src/` 전체에서 주석을 뺀 문자열·HTML 텍스트 중 한글이 든 것을 셌다.

| 파일 | 문자열 | 그중 보간(`${}`) 포함 |
|---|--:|--:|
| `content/commands.js` | 103 | 46 |
| `shared/defaults.js` | 55 | 0 |
| `content/sidebar.js` | 45 | 16 |
| `content/index.js` | 29 | 7 |
| `content/tty.js` | 13 | 3 |
| `content/health.js` | 7 | 1 |
| `popup/popup.html` · `popup.js` | 10 | 0 |
| `background/service-worker.js` | 4 | 0 |
| `options/options.js` · `options.html` | 7 | 3 |
| 나머지 8개 파일 | 22 | 3 |
| **합계** | **295** | **79** |

`defaults.js` 의 55개는 설정 항목의 라벨·도움말·선택지다. 한 배열(`GT_SCHEMA`)에
모여 있어 손대기 가장 쉽다. 반대로 `commands.js` 의 103개는 명령마다 흩어져 있고
절반 가까이가 보간을 낀다.

**로케일에 걸리는 것이 문자열만은 아니다.**

```
toLocaleTimeString('ko-KR', …)   4곳   (tty.js 3, options.js 1)
chrome.i18n 사용                  0곳
Intl 사용                         0곳
manifest.default_locale          없음
_locales/                        없음
```

## 2. 크롬의 기본 방식으로 되는 것과 안 되는 것

`_locales/<lang>/messages.json` + `chrome.i18n.getMessage()` 가 표준이다.

**되는 것**

- 매니페스트의 `name`·`description` 을 `__MSG_key__` 로 지역화 → **스토어 리스팅이
  브라우저 언어에 따라 바뀐다.** 이건 이 방식으로만 된다
- 콘텐츠 스크립트(isolated world)·팝업·옵션·서비스 워커에서 `chrome.i18n` 사용 가능
- `$1` 형태의 자리표시자 지원 → 보간 79개를 담을 수 있다

**안 되는 것 — 이 앱에서 걸리는 지점**

| 제약 | 왜 문제인가 |
|---|---|
| **언어를 앱 안에서 못 바꾼다** | `chrome.i18n` 은 **브라우저 UI 언어**를 따른다. 크롬 자체 설정을 바꾸고 재시작해야 한다. 이 앱은 이미 `:set` 과 옵션 화면으로 모든 것을 바꾸는 제품이라 어긋난다 |
| **MAIN world 에서 못 쓴다** | `src/main/tap.js` 는 페이지 월드라 `chrome.*` 가 없다. 지금 거기서 만든 문구(`window.fetch 가 함수가 아닙니다` 등)가 `postMessage` 로 화면에 오른다 |
| **런타임에 사전을 못 고친다** | 테스트에서 문구를 바꿔 끼우기 어렵다. 지금 회귀 테스트 상당수가 문구를 정규식으로 붙잡고 있다 |

## 3. 방안 세 가지

### A. `chrome.i18n` 만 쓴다

- 장점 — 표준. 추가 코드가 거의 없다. 스토어 리스팅 지역화가 딸려 온다
- 단점 — **앱 안에서 언어 전환 불가.** MAIN world 는 별도 처리 필요
- 규모 — `_locales/ko/messages.json`, `_locales/en/messages.json` 각 295키

### B. 자체 사전 + `t()` 만 쓴다

- 장점 — `locale` 설정을 `GT_SCHEMA` 에 넣어 **앱 안에서 즉시 전환**. 이미 있는
  설정 반영 경로(`config.onChange` → `applyConfig` → 다시 그림)를 그대로 탄다.
  MAIN world 에는 문구 대신 **코드**를 보내 isolated 에서 번역하면 된다
- 단점 — **스토어 리스팅은 지역화되지 않는다**(매니페스트는 `_locales` 만 읽는다)
- 규모 — `src/shared/i18n.js` + 로케일 파일 2개

### C. 둘을 섞는다 ← **추천**

- 매니페스트(`name`·`description`)만 `_locales` 로 → 스토어 리스팅 지역화
- 화면 문구는 자체 사전 `t()` 로 → 앱 안에서 전환 가능
- 두 사전이 겹치는 건 이름·설명 **두 줄뿐**이라 중복 관리 비용이 거의 없다

## 4. C 안으로 갈 때의 설계

```js
// src/shared/i18n.js — 콘텐츠·팝업·옵션이 공유한다
var GT_I18N = {
  ko: { 'cmd.rename.ok': '이름 변경: $1', … },
  en: { 'cmd.rename.ok': 'Renamed: $1', … }
};
var GT_T = function (key, ...args) { … };   // 없으면 키를 그대로 돌려준다
```

- **키 이름은 화면 위치를 따른다** — `cmd.*`, `sidebar.*`, `popup.*`, `opt.*`, `health.*`
- **보간은 `$1` 로 바꾼다.** 지금의 `` `이름 변경: ${name}` `` → `t('cmd.rename.ok', name)`.
  79곳이 이 작업 대상이다
- **언어 선택은 설정 항목으로.** `GT_SCHEMA` 에 `locale`(`auto`/`ko`/`en`) 추가.
  `auto` 는 `navigator.language` 를 본다
- **MAIN world 는 코드만 보낸다.** `post('broken', {reason:'fetch-missing'})` 로 바꾸고
  isolated 쪽에서 `t('health.fetchMissing')` 로 번역한다. 지금은 완성된 한국어 문장을
  보내고 있다
- **시각 표기.** `toLocaleTimeString('ko-KR', …)` 4곳을 현재 로케일로 바꾼다.
  `timestamps: 'relative'` 의 '3분 전' 같은 표현도 문구다

## 5. 테스트에 미치는 영향 — 여기가 진짜 비용이다

지금 회귀 테스트가 **화면 문구를 정규식으로 붙잡고 있다.** 문구가 키로 바뀌면
그 단언들이 통째로 흔들린다.

```
convops   '되돌릴 수 없습니다' · '대상: ${c.title}'
messup    '서버로 가지 않습니다' · '걷어낼 것이 없습니다'
thinking  '자리표시자를 응답으로 삼으면'
lifecycle '확장이 다시 로드 됐습니다' · '새로고침해주세요'
preflight '모듈이 로드되지 않았습니다'
```

**문구 대신 키를 붙잡도록 바꿔야 한다.** 예: `/t\('convops\.rmConfirm'/`.
그러면 번역이 늘어도 테스트가 안 깨진다.

여기에 **새로 필요한 검사**가 생긴다.

- 모든 로케일이 같은 키 집합을 갖는가 (빠진 키 = 화면에 키가 그대로 노출)
- 보간 자리표시자 개수가 로케일 간에 일치하는가 (`$1` 만 쓰고 `$2` 를 빠뜨리면 깨진다)
- 소스에서 부르는 키가 사전에 실재하는가

지금의 존댓말 검사(`store.listing.test.mjs`)는 **한국어 사전에만** 적용하도록
좁히면 된다. 오히려 사전 한 곳만 보면 되니 지금보다 단순해진다.

## 6. 규모 감각

| 단계 | 대상 | 성격 |
|---|--:|---|
| 1. 뼈대 | `i18n.js`, `locale` 설정, 매니페스트 `_locales` | 새 코드. 작다 |
| 2. 설정 화면 | `defaults.js` 55개 | 배열 한 곳. 기계적 |
| 3. 팝업·옵션·배지 | 21개 | 작다 |
| 4. 명령·사이드바 | 148개 (보간 62) | **가장 큼.** 보간을 `$1` 로 바꾸는 일 |
| 5. 나머지·시각 표기 | 71개 + `toLocale` 4곳 | 중간 |
| 6. 테스트 전환 | 문구 단언 → 키 단언 | **비용의 절반은 여기** |

## 7. 판단

**지금 당장 해야 하는 일은 아니다.** 아직 개인용에 가깝고, 스토어 제출도 준비만
해 둔 상태다. 다만 **문구를 만질 때마다 비용이 늘어난다** — 이번에 존댓말로 바꾸며
295개를 한 번 훑었는데, 다국어를 먼저 넣었다면 사전 한 곳만 고쳤을 일이었다.

권하는 순서는 이렇다.

1. **키 체계를 먼저 정하고 뼈대만 넣는다**(1단계). 사전은 한국어 하나로 시작한다.
   이 시점에는 화면이 하나도 안 바뀌므로 위험이 없다
2. 이후 **문구를 고칠 일이 생길 때마다 그 파일을 사전으로 옮긴다.** 한꺼번에
   295개를 옮기지 않는다
3. 영어 사전은 스토어 제출을 실제로 진행할 때 채운다

## 1단계·2단계 완료 (2026-09-08)

권한 순서대로 뼈대와 설정 화면까지 넣었다.

- `src/shared/i18n.js` — 사전(`ko`·`en`) + `GT_T()` + `GT_SET_LOCALE()`.
  없는 키는 **키를 그대로 돌려준다.** 빈 문자열이면 화면에서 조용히 사라져
  무엇이 빠졌는지 알 수 없다
- `GT_SCHEMA` 에서 문구를 **전부 걷어냈다.** 라벨·도움말·선택지는 규칙으로 만든 키
  (`opt.<key>.label` 등)로 사전에서 꺼낸다. 스키마에 한글이 남아 있지 않은지 테스트가 본다
- `locale` 설정 추가(`auto`/`ko`/`en`). `auto` 는 `navigator.language` 를 본다.
  바꾸면 `config.onChange` → `applyConfig`(epoch 증가) → 전부 다시 그림
- 매니페스트는 `__MSG_extName__` / `__MSG_extDesc__` 로 두고 `_locales/{ko,en}` 추가.
  **스토어 리스팅이 브라우저 언어를 따라간다**
- `tools/package.sh` 가 `_locales` 를 담고, `default_locale` 을 선언했는데 메시지
  파일이 없으면 **막는다.** 그 상태면 크롬이 확장을 아예 로드하지 않는다

`test/i18n.test.mjs` 40건 — 로케일 간 키 집합 일치, 자리표시자 일치, 스키마가 쓰는
키의 존재, 죽은 키 없음, 폴백, 매니페스트 `_locales` 배선까지.

옵션 화면을 ko·en 으로 렌더해 눈으로 확인했다.
